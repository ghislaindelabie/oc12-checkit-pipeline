CheckIt.AI — Pipeline d'acquisition de données multimodales

Projet de formation AI Engineer — détection de désinformation (texte + image appariés)

Ghislain Delabie · rapport de projet · juin 2026

5 livrables ~1,02 M d'articles en base 13 sources intégrées 132 tests Airflow 3.2 · PostgreSQL 16 · Streamlit

Ce rapport retrace les cinq étapes du projet : pour chacune, ce qui a été réalisé, le raisonnement derrière les choix, les outils retenus et les résultats mesurés. Le fil rouge : la valeur du jeu de données tient à l'appariement texte↔image et à la qualité des labels, pas au volume brut.

Résumé exécutif

Un pipeline Python modulaire acquiert des publications multimodales depuis trois couches de sources (corpus annotés, agrégateurs de fact-checking, connecteurs live), les normalise vers un schéma commun, les charge dans une base PostgreSQL sécurisée via Apache Airflow, et expose des KPI sur un tableau de bord Streamlit assorti d'un plan de monitoring. Toutes les sources sont qualifiées sur leur document de droits contraignant ; les images sont conservées localement, jamais redistribuées.

Architecture d'ensemble

Trois couches de sources convergent vers une chaîne unique extract → transform → load, orchestrée par Airflow selon trois cadences distinctes (corpus une fois, fact-checking hebdomadaire, flux live quotidien).

Corpus annotés DGM4 · Fakeddit · FakeNewsNet ─┐ DAG @once Fact-checking ClaimReview · EUvsDisinfo · Google FCT ─┤ DAG @weekly APIs presse + RSS GDELT · Guardian(+6) · RSS FR · satire ─┼─ extract ─▶ JSONL (brut) Réseau social Bluesky ─┘ DAG @daily │ transform ─▶ Parquet + index CSV │ load (idempotent) ─▶ PostgreSQL 16 sécurisé + images sur disque │ Streamlit : KPI (appariement · validité · rapidité · coût)

Pourquoi trois couches ? Les corpus annotés portent les labels (vérité terrain) ; les agrégateurs de fact-checking fournissent une source de vérité réutilisable ; les connecteurs live démontrent l'acquisition automatisée exigée par la mission. Chaque faiblesse d'une source est compensée par une autre.

Étape 1 — Explorer et qualifier les sources

1

Objectif. Identifier ≥ 3 sources multimodales pertinentes, décrire format, langue, qualité des labels et méthode d'extraction ; vérifier les droits d'usage.

Réalisé. 86 sources examinées sur 5 axes (modalité appariée, format, langue, qualité des labels, droits) ; 13 vérifiées sur pièces et intégrées. Rapport : deliverables/step1/rapport-exploration-sources.md.

Choix structurant. Juger les droits sur le document contraignant (CGU/licence/robots.txt), jamais le marketing. Cela a, par ex., disqualifié NewsData.io comme « usage commercial » (CGU illisibles), promu GDELT (CGU lue : usage libre + attribution), et écarté Telegram/Mastodon (clauses anti-collecte).

Outils : WebFetch/WebSearch pour la vérification des CGU, urllib.robotparser, sondes requests pour mesurer le taux de remplissage des champs image en conditions réelles.

Étape 2 — Scripts d'extraction automatisée

2

Objectif. Scripts Python modulaires, exécutables sans intervention, sauvegardant des données structurées.

Réalisé. Un paquet checkit/ où chaque source a son adaptateur derrière une enveloppe commune ; 7 adaptateurs d'APIs presse déclaratifs ; sonde RSS ; client Bluesky ; téléchargeurs de corpus. CLI unique : python -m checkit.extract --source <nom>.

Conception. Fonctions pures (connexion / parsing / nettoyage / sauvegarde) sans dépendance à Airflow → l'étape 4 les enveloppe sans refactor. Régulation de débit partagée par clé (GDELT 5,5 s = limite énoncée par l'API, etc., cf. docs/rate-limits.md). Motif skip-if-no-key : une source sans clé est ignorée, jamais une erreur. Appariement vérifié avant écriture (image téléchargeable + valide).

Outils : requests+tenacity, feedparser, BeautifulSoup/trafilatura, Pillow+imagehash, pydantic-settings (secrets via SecretStr), logs JSON, pytest+responses.

Étape 3 — Pipeline de transformation + schéma conceptuel

3

Objectif. Transformer le brut en jeu exploitable (nettoyage, normalisation, mapping), de façon reproductible et journalisée ; documenter par un schéma conceptuel.

Réalisé. Étapes lecture / traitement / export : nettoyage de texte, normalisation des labels de 6 taxonomies vers {real, fake, satire, unverified}, qualification de l'appariement, déduplication, export Parquet + index CSV, et un RunReport JSON (les KPI consommés ensuite). Schéma conceptuel Mermaid (docs/conceptual_schema.md), distinct du modèle physique.

Brut = fidélité, transformé = interprétation. Les entiers de label Fakeddit ont été calés empiriquement (croisement subreddit↔label sur 680 K lignes, zéro bruit). L'exécution complète a révélé deux bugs d'identité (DGM4, ClaimReview), corrigés avec tests de non-régression — la déduplication DGM4 retombe alors exactement sur les 230 000 échantillons canoniques du papier (preuve d'intégrité).

Outils : pandas 2.2+pyarrow (lisibilité > polars à cette échelle), Parquet (typé, colonnaire, prêt ML), Mermaid. Format : JSONL (brut) → Parquet + index CSV (propre).

Étape 4 — Orchestration Airflow → base sécurisée

4

Objectif. Flux ETL Airflow avec tâches distinctes, chargement dans une base SQL/NoSQL adaptée et sécurisée, exécutable en local.

Réalisé. Trois DAGs (Astro CLI, Airflow 3.2) aux tâches minces qui délèguent au paquet testé ; XCom ne transporte que des chemins. PostgreSQL 16 (conteneur dédié). Chargement idempotent (ON CONFLICT DO NOTHING) avec porte de qualité (abandon si validité < 50 %). Preuves : deliverables/step4/preuves-execution.md.

SQL plutôt que NoSQL : problème relationnel (contrainte d'unicité = dédup + KPI doublons gratuits, jointure propre vers les métriques). Sécurité (3 axes du brief) : authentification scram-sha-256, rôles à moindre privilège (etl_writer/dashboard_reader), chiffrement pgcrypto. Robustesse prouvée en réel : un échec de permission a été absorbé par retries=3 (la tâche a réussi à la tentative suivante).

Outils : Apache Airflow 3.2 (Astro CLI/Docker), PostgreSQL 16, psycopg3. Preuve d'idempotence : 978 289 lignes insérées, puis re-run = 0 insérée / 978 289 ignorées.

Étape 5 — KPI, tableau de bord & monitoring

5

Objectif. Définir des KPI (précision, rapidité, coût), un tableau de bord lisible par un public non technique, et un plan de monitoring cohérent avec les automatisations.

Réalisé. Tableau de bord Streamlit (FR) : cartes KPI, répartition des labels, volumes par source, qualité au fil des exécutions avec le seuil d'arrêt tracé ; lecture en rôle lecture seule, cache 5 min, garde-fous base éteinte / aucune exécution. Plan de monitoring (docs/plan-monitoring.md).

Honnêteté du plan. Chaque seuil est étiqueté Appliqué (dans le code : porte qualité, retries, timeout), Observé (affiché) ou Non câblé (stub d'alerte documenté) — rien n'est promis que le code ne fasse réellement.

Outils : Streamlit 1.58 (st.metric, st.connection), Plotly. La logique KPI vit dans un module sans UI → testée unitairement.

EUvsDisinfo — décision de méthode. Le site live est protégé par un challenge Cloudflare et son robots.txt interdit la recherche/pagination. Plutôt que de contourner une protection anti-bot (contraire à notre posture et au droit), nous avons utilisé le miroir ouvert officiel (Zenodo, CC-BY-4.0) puis enrichi le texte/image avec notre propre pile — un meilleur choix sur tous les plans (légal, reproductibilité, effort).

L'enveloppe commune RawRecord

Chaque source parle un dialecte différent (GDELT dit socialimage, NewsData dit image_url…). Chaque adaptateur traduit vers une enveloppe unique validée à l'entrée (Pydantic), ce qui permet une seule chaîne de transformation pour les 13 sources.

  • Identité déterministe (record_id = UUID5 du contenu) → chargements idempotents.
  • Champs standardisés : titre, texte, légende, image_url, langue, date (UTC), domaine, provenance.
  • extras : tout le spécifique source conservé intact (labels bruts, grounding…) — interprété seulement à l'étape 3.
  • RGPD : identifiants d'auteurs sociaux pseudonymisés (hash salé), jamais en clair.

La satire est une classe à part entière (jamais fusionnée avec la désinformation) ; les cas limites portent un drapeau ambiguous. On ne confond pas opinion controversée et désinformation : seules les affirmations factuelles vérifiables reçoivent un label de véracité.

Qualité & méthode de travail

  • TDD systématique — 132 tests hermétiques (< 10 s, zéro réseau) ; chaque étape gated par les tests.
  • Validation live après chaque composant — a révélé 6+ pièges qu'un test unitaire ne voit pas (flux satire sans image en flux → repli og:image, vrai throttle GDELT, comportement WAF Bluesky, limite de champ CSV Fakeddit, identités DGM4/ClaimReview, binding réseau de la base).
  • Git discipliné — branches de fonctionnalité + PR, commits conventionnels.
  • Données volumineuses hors dépôt — tout sur le disque secondaire /data/files/OC12.

Conformité & droits

  • Droits jugés sur le document contraignant ; canaux officiels d'abord ; scraping en dernier recours.
  • Images conservées localement (chemin + SHA-256 + pHash), jamais redistribuées.
  • Régulation de débit par clé/domaine alignée sur les limites énoncées (docs/rate-limits.md).
  • Secrets en .env non versionné ; colonne sensible chiffrée (pgcrypto).
  • EUvsDisinfo : refus explicite de contourner Cloudflare/robots → miroir ouvert officiel.

Ce qui reste

Tous les livrables existent et fonctionnent. Restent des finitions : captures d'écran de l'UI Airflow (pour la preuve d'exécution), enrichissement image complet de FakeNewsNet, réglage fin de la requête FR de GDELT, et l'enregistrement des clés d'APIs presse restantes (le pipeline tourne déjà sans elles).
